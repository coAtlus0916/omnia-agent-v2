# ADR-0020：功能菜单最多三级，允许二级直接作为 Feature

状态：Accepted  
日期：2026-07-30  
决策者：用户  
Refines：ADR-0010/ADR-0012 中“三级功能树”的深度语义；不改变三列 Shell 或历史首批范围记录

## Context

v5 第二列需要从 v4 的 Agent/用户列表改为功能树。早期草案把所有业务入口强制建模为“一级业务域 → 二级能力组 → 三级 Feature”，但部分业务域下只有少量功能，强制增加能力组会制造只有一个叶子的空洞层级，增加点击和视觉噪音。

用户决定菜单不强制三级，有些功能使用两级即可。

## Decision

1. 功能树最大深度为三级，不是固定三级。
2. 一级必须是业务域 `group`，不能直接执行。
3. 二级可以是：
   - `feature`：直接可运行的两级入口；
   - `group`：确有多个相关能力时继续展开。
4. 三级只能是 `feature`，不再继续嵌套。
5. Feature 可运行性由 `kind=feature` 和真实后台状态决定，不由层级决定。
6. 不为满足形式创建只有一个业务叶子的二级分组；分组应表达稳定、对用户有意义的能力集合。
7. Feature ID、版本、route、权限、Run 和历史记录独立于导航 parent。以后从二级移动到三级或反向移动，不改变 Feature 身份。
8. 当前首批建议使用混合深度：

```text
其他
├─ 元素管理
│  ├─ 新建与关联
│  └─ 删除元素
├─ 删除聊天记录
└─ 录制
```

9. 导航仍完全来自后台 Feature Registry；未接真实能力的叶子不出现或明确 disabled，前端不得硬编码占位项。

## Consequences

- 少量功能可以一步进入，界面更接近紧凑桌面工具。
- 同一棵树需要同时支持 level 2/3 Feature 叶子的键盘、焦点、展开、搜索、权限和状态逻辑。
- Feature Package manifest 的 navigation 从固定 `level1/level2/level3` 改为最大三段的 path/node 声明。
- 菜单重组不会破坏路由、数据或历史 Run，但需要发布新的导航 snapshot/stateVersion。
- 二级分组是否有意义成为产品信息架构评审项，而不是技术强制项。

## Alternatives

### 所有功能强制三级

拒绝。会为单一入口制造无价值分组，增加操作成本。

### 所有功能固定两级

拒绝。元素管理等相关功能增多时会失去清晰归类。

### 允许任意深度

拒绝。增加导航、键盘、可访问性和迁移复杂度，不符合紧凑桌面产品目标。

## Verification

- 合同允许 level 2/3 的 `kind=feature`；
- level 1 必须 group，level 3 必须 feature，禁止 level 4；
- 混合深度树的鼠标、键盘、焦点、搜索、折叠和恢复测试通过；
- Feature 移动 parent 后 ID、route、权限和历史 Run 不变；
- 后端未注册/不健康/未授权 Feature 不因前端硬编码出现；
- 首批混合结构在 Windows 缩放和紧凑密度下完成可用性评审。
